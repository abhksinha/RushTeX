# TeX's weaknesses to remove: same visual output, cleaner files, least resources
Author: abhi+claude | Date: 2026-10-20 (living tracker: update in place as items close)
Files: `src/lib.rs`, `src/frontend/frontend_ast.rs`, `src/expand/expand_mod.rs`, `src/layout/layout_engine.rs`, `src/layout/layout_linebreak.rs`, `src/layout/layout_pagebuilder.rs`, `src/frontend/frontend_parser.rs`, `src/math/math_layout.rs`, `src/backend/backend_pdf.rs`, `src/backend/backend_pdftex.rs`, `src/backend/backend_scaled.rs`, `src/backend/backend_fonts.rs`, `src/backend/backend_optical.rs`, `src/backend/backend_cm_fonts.rs`, `src/backend/backend_cm_fix.rs`, `src/backend/backend_ts1.rs`, `scripts/parity/parity.py`

## Context
The project goal is a superset of LaTeX. The user asked for a record of TeX's architectural weaknesses that RushTeX should remove. The output must stay visually identical to pdfLaTeX, with zero shift as `parity.py exact` measures it. The PDF files should be cleaner and smaller, and the engine should use as few resources as possible. TeX's rules (tex.web, latex.ltx) are the values to reproduce. Its 1978 machine-driven methods are what we may replace.

## Decision
Invariant: compatibility mode reproduces pdfTeX's glyph positions exactly. Every item below must keep `exact` at its current level and strict at 100%.

How the work proceeds:
- Superset behaviour is opt-in only.
- An item is closed when it is measured, covering time, peak memory, binary size and PDF size.
- Order (user priority, 2026-10-20): the pack format (17) with the font architecture (18) first, then the exact integer core, then the explicit state model, then compatibility as data (whose output is packs), then semantic output, then incremental compilation, then the superset layer. The pack format comes first because every later item emits into it: the macro engine's snapshots, fonts, hyphenation and class tables. Designing it first avoids reworking them.

## Rejected
- Reimplementing TeX's methods literally, such as the digit-loop `divide_scaled`, the `mem` array and linked-list nodes. Values are kept, methods are ours (user rule, 2026-10-20).
- Changing default layout behaviour to look "better" than TeX, for example global page optimisation by default. That breaks the identical-output invariant. Such behaviour is opt-in only.
- Splitting the engine's code into dynamic libraries ("mini-binaries"): symbol tables, loader and relocation overhead, no LTO or inlining across modules, and no usable dynamic linking on wasm. pdfTeX itself is one binary; TeX Live's weight is data. Split data, not code.
- Interpolating CM design sizes from a few master outlines: much smaller storage, but glyph shapes differ from pdfLaTeX's, which breaks identical output. Opt-in only.
- A general-purpose `HashMap` for font lookups: encodings are 256-entry arrays (direct index); Unicode lookup is a static perfect hash built at build time. Hashing is used to deduplicate outlines, not as the lookup structure.
- A Bloom filter per block for macro dependencies (item 4): it does not pinpoint. It needs a scan of every block anyway and gives false positives of about 13% at 128 bits and 2.6% at 256 bits for 30 macros per block. The flat sorted array is exact at 2 bytes per link.
- A forward plus reverse macro index (item 4): about 6 bytes per link and two structures to keep in step, for an event (a definition change) that happens rarely.
- Hash maps and Bloom filters by default. They go only where keys are dynamic or most lookups miss, and only when measured.

## Open
Each item lists the weakness, our remedy, and the resource effect.

1. **Mixed number representation (ours, inherited risk).** TeX is exact in integer sp; float boundaries in our code drift. Remedy: one 4-byte sp length type in layout, math and `Paint`, with floats only for glue ratios as in TeX. Resources: same memory, integer arithmetic. Status: `Paint` coordinates are under way; vertical `self.y` and math are still f32.
2. **Multi-pass via `.aux` files.** References, `\pageref`, TOC and citations need reruns and disk files. Remedy: in-process fixpoint. The dry layout records label pages, and the second expansion runs only when `\pageref` occurs; we already do this. Next: re-layout only from the first page whose numbers changed. Resources: no files, one pass for most documents.
3. **Global mutable state** (registers, catcodes, `\every...` hooks). Nothing can be cached or run in parallel, and dependencies are hidden. Remedy: immutable state snapshots with per-group deltas. Each paragraph records a bitmap of the state it read. Resources: deltas instead of copies; read-sets are small bitmaps.
4. **No incremental compilation.** Every edit reruns everything. Target: under 1 ms per keystroke whatever the document length (full compile of the six corpus documents is already 2 to 9 ms; the gain is for 100+ page documents and live preview). Needs item 3 (the read-set makes cache keys correct) and item 1 (cached results must be exact).
   - Unit: the block, any top-level vertical-list item: paragraph, display equation, table, float, list item, heading, footnote, table of contents. Key = 64-bit hash of its input bytes plus the values of the state it read (fonts, `\hsize`, counters, macros used). Value = its laid-out boxes (`Paint` ops, line descriptors).
   - Caching is nested (page, block, line, formula or cell), so an unchanged piece inside a changed block is reused.
     - Display equations: the body is cached apart from its number; inserting an equation redraws later numbers only, bodies are reused.
     - Inline math: each formula cached by source, style and size; editing the text around it re-breaks the paragraph and reuses the formula.
     - Tables: each cell cached; a column keeps its widest cell. An edit that neither was nor becomes the widest re-lays one row; a width change shifts rows (positions only, contents cached). `p{}` cells cache like paragraphs; `longtable` follows page re-flow.
     - Floats: body cached, placement redone only when the surrounding pages re-flow. Lists: each item cached, item numbers like equation numbers. Footnotes cache like paragraphs; placement follows page building.
     - Table of contents: depends on the heading list; a heading edit re-lays it, and a length change re-flows until convergence.
     - Preamble and document-wide changes (`\textwidth`, base size) force a large relayout; blocks whose key is unchanged are still reused.
   - Parse: re-parse from the edited offset, back in step at the next blank line.
   - Macro dependencies: one flat `u16` array of document-local macro ids, each block's list sorted and deduplicated (a per-id bit cleared after the block), plus one `u32` start offset per block. Macros expanded indirectly count. On a definition change, scan the blocks and binary-search each list: about 25,000 compares for 5,000 blocks, 20 to 50 µs (estimate), exact. A recomputed block overwrites its list; there is no reverse structure to maintain. 2 bytes per link. A `\renewcommand` inside the body is positional state, already in the state key, so it is not tracked here; nor are primitives. Definition changes are rare while typing (mostly preamble edits), so memory and maintenance matter more than lookup speed. Upgrade only if scans measure hot (10k+ pages or frequent body redefinitions): per-macro delta-encoded block lists (about 1 byte per link), switching to a bitmap over blocks for macros used by more than 1 in 8 blocks (Roaring-style).
   - Line breaking: cached breaks reused unless the key changed.
   - Page building: restart from the first changed paragraph; stop when the page builder's state at a paragraph boundary equals the old run's (page total, pending insertions and floats, marks, counters). All later pages are reused. `\flushbottom` can carry a shift to the end, but line breaks stay cached, so only page building and changed page streams are redone.
   - Counters and references: equation and section numbers are part of the state key; a changed label value invalidates the paragraphs that `\ref` or `\pageref` it, through the same dependency record.
   - PDF: each page's content stream is cached as bytes; only changed pages are re-emitted, the rest are memory copies. Font objects are rewritten only when the used-glyph bitmap grows.
   - Hashing: our own fast non-cryptographic 64-bit hash, no new dependency; debug builds re-check cache hits against a fresh computation.
   - Expected (estimates, to measure): typing inside a paragraph without changing its line count re-breaks one paragraph (10 to 50 µs) and re-emits one page (about 50 µs); an edit adding a line re-flows until state converges, usually 1 to 2 pages; worst case a few ms on 500 pages.
   - Correctness: incremental output must be byte-identical to a full compile. CI fuzzes random edits over the corpus and compares PDF bytes; any difference fails.
   - Memory: the existing compact layout data plus about 16 bytes of key per paragraph, a few MB for 500 pages, bounded by an LRU.
   - API: a library `Session` with `apply_edit(range, text)` returning the changed pages; a CLI `--watch`; wasm live preview.
   - Base: the streaming path (`Parser::parse_next_block` then `Layouter::layout_stream_block`) already works block by block; the full-AST path (TOC documents) needs the same fixpoint loop.
5. **Serial by construction.** Line breaking waits on global state. Remedy: once item 3 exists, break paragraphs in parallel; keep the PDF writer pipelined (it is today, behind `--threads`). Serial stays the default for low resource use.
6. **Macro expansion as the only extension mechanism.** It is slow, opaque and has poor errors. Remedy: a minimal macro engine runs the real `.cls`, `.clo` and `.sty` files at build time into a baked format snapshot (TeX's §1299 idea): flat register arrays, an interned control-sequence table and a token arena, embedded with `include_bytes!`. Hot paths get native fast paths, proven equal to the macros by differential tests. Resources: classes become KBs of data instead of Rust code; no runtime parsing of class files.
7. **Font encodings fragment the character set** (OT1, T1, TS1, OMS, OML, OMX). This causes `\$`, `\textbullet` and accent pain. Remedy: internally map Unicode to (font, glyph), with encodings as generated tables (`TS1_TEXT_SYMBOLS`, slot maps). Kerns are stored as TFM stores them, as an index into the distinct fix_words (done 2026-10-20). Resources: tables are static and binary-searched.
8. **Whole fonts embedded per encoding and size.** Remedy: subset at write time, using a used-glyph bitmap per font (2 x u64 for 128 codes) and emitting only those charstrings. Resources: PDF size drops; the TS1 masters alone add 13 KB each today.
9. **Lost document semantics.** Boxes and glue forget headings, lists and equations, hence poor accessibility, no HTML and weak copy-paste. Remedy: keep the AST linked to the layout and emit tagged PDF (PDF/UA), reflowable HTML and SVG from one layout. ToUnicode for the math fonts already exists, and `exact` reports it as `other-text`. Resources: structure tags are a few bytes per block.
10. **Greedy page builder and float placement.** These are local decisions only. Remedy: keep TeX's algorithm as the default (identical output); offer opt-in global page and float optimisation (Knuth-Plass over pages) as a superset feature.
11. **Errors stop the run and are cryptic.** Remedy: resilient parsing, span diagnostics with suggestions (exists), and a gap inventory that never stops (`--gaps`). Next: recovery that still produces a PDF with error markers.
12. **Distribution weight.** TeX Live is about 5 GB, with kpathsea file searches. Remedy: a single binary (it also builds for wasm), with no file system search at run time. Packages come as content-addressed precompiled snapshots fetched on demand and verified by hash.
13. **Verification is one torture test (trip).** Remedy: pdfTeX as a live oracle, glyph by glyph (`parity.py score/exact/boxes`). Next: CI budgets that fail on regressions in exact %, time, peak RSS, binary size and PDF size. Also check rules, not only glyphs.
14. **Content stream verbosity** (pdfTeX writes one operator per position change). Remedy: same positions, compact stream. One `TJ` array per line where positions allow (done); colour only on change; deflate on (exists). Next: measure PDF bytes against pdfLaTeX per document and track it.
15. **Fixed-size memory and linked nodes** (`mem` array, pointer chasing). Remedy: arenas, SoA paragraph data, 24-byte `Paint` and 16-byte line descriptors, borrowed `&str` AST, and scratch buffers reused across pages. Rule: no per-glyph allocation. Known leftover: number and label measurement allocates a small `Vec` per call.
16. **Diagrams through macros** (TikZ and PGF interpret drawing in TeX macros, which is slow and memory heavy). Remedy: a native diagram engine with constraint layout that emits boxes, rules and paths. It never changes how the core behaves. Optional TikZ-subset front end later.
17. **Monolith versus installer (first priority).** TeX Live is about 5 GB of data that kpathsea searches file by file; our 3.4 MB binary embeds every font and pattern whether a document uses it or not. Remedy: one small engine binary plus data packs loaded on demand.
   - Engine: code plus a minimal kernel (CM at 10pt, English hyphenation, `article`). Target 1 to 1.5 MB stripped.
   - Packs: one per font family, language, class or package snapshot. Each is a flat precompiled file with a versioned header and offset tables. It is read once and indexed in place, with no parsing and no copy; native code reads the file, wasm uses `fetch`.
   - Content-addressed: a pack is named by the hash of its bytes, so it is verified, cached forever and safe to fetch. Packs are data only and never contain code.
   - Pack index: one hash lookup from a name to its pack, replacing kpathsea's path search.
   - The `embed-all` build feature keeps today's self-contained monolith (same packs via `include_bytes!`), so offline and single-file use stay one codebase.
   - Measured 2026-10-20: binary 3,408,808 bytes; `assets/cm_fonts` 916 KB (67 files); hyphenation source 750 KB; math font tables source 291 KB; engine code the rest, with debug symbols still in it.
   - Size budget at completion (estimate): engine 1 to 2 MB. Packs for the common LaTeX set (CM, Latin Modern, AMS fonts, TS1, about 80 hyphenation languages, the core classes and the 200 most used packages) under 50 MB. Every CTAN font as well could reach 100 to 200 MB, because fonts dominate (cm-super alone is about 60 MB). The working set per document stays 1 to 5 MB; the total download is whatever the user actually uses.
   - Steps: strip symbols and measure the true code size; define the pack format; move CM fonts and hyphenation into packs with `embed-all` the default so nothing breaks; then make the macro engine's class and package snapshots packs.

18. **Font architecture (part of 17, first priority).** The weakness is in TeX and in ours: TeX splits fonts by encoding and design size into whole files; we copy that and add our own problems.
   - Problems today: `Face` is a hard-coded enum (42 faces plus 31 design-size masters in `backend_optical.rs`), so adding a font is a code change. Widths have three sources (TFM fix_words, old per-face tables via `resolve_width_table_at`, AFM tenths for Base-14), which is why `section_number_width` has two branches. Every encoding and design size is a separate whole embedded font, so a glyph shared between encodings is stored once per font. Encodings are baked into fonts: TS1 has its own fonts, ToUnicode and `Face`. No subsetting.
   - Remedy, four flat layers:
     1. Glyph store: every unique outline stored once, keyed by a hash of its charstring; a font is a list of glyph ids. Sharing is across encodings; design sizes have truly different outlines.
     2. Metrics apart from outlines: one block per face and design size (widths, heights, depths, italic corrections, kerns, ligatures, parameters), each value an index into the font's distinct values, which is TFM's own layout (done for kerns). One width source, integer sp, no f32 tables.
     3. Encodings as tables: 256-entry arrays for OT1, T1, TS1, OML, OMS, OMX; a static perfect hash from Unicode to glyph.
     4. Fonts as pack records (outline source, metric block, encoding). NFSS selection resolves through a pack index built from the `.fd` data, so `Face` stops being a fixed list.
   - PDF output: a used-glyph bitmap per font (2 or 4 u64); write only those charstrings and the subroutines they need. Font names, `/Widths` and ToUnicode stay as pdfTeX writes them.
   - Steps: measure outline duplication across the 67 fonts in `assets/cm_fonts` first; unify widths into one TFM-exact source; turn faces into records; build the glyph store and subsetting in the pack format.
